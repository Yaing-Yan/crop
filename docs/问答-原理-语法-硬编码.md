# CROP 问答实录：原理 / 语法 / 硬编码 / 优化性质

> 记录两次问答，供打印研读。
> 仓库：<https://github.com/Yaing-Yan/crop>（GPL-3.0-or-later），机型 CASIO fx-991 CN X（nX-U16 / ePS-16）。

## 问答一：原理是什么？有脱离原本的 C 语法糖吗？有硬编码吗？

### 1. 原理

```
C 源码 ──rGCC──► .bin（真正的 nX-U16 机器码） ──解释器──► ROP 链（4 字节槽序列）──► 机器
```

**第一层：rGCC 只生成"ROM 里存在等价 gadget 的指令形态"。**
它输出的 `.bin` 是一段货真价实的 nX-U16 程序；生成后立刻逐条核对"能不能在 ROM 里
找到**字节完全相同、且后面紧跟 `POP PC`** 的块"，找不到就报错（不生成错代码）。

**第二层：解释器把 `.bin` 切成"最长可匹配块"。**
每一块在 ROM 里逐字节相同 + 紧跟 `POP PC` ⇒ 变成链上的**一个 4 字节槽**：

```
一个槽 = [PC_lo][PC_hi][CSR_lo][CSR_hi]      （POP PC 取走 PC(2)+CSR(2)，CSR 只取低 4 位）
```

ROM 里没有现成块的单条指令走**等价转义**（L2），例如
`MOV Rn,#imm` → `POP Rn` + 链上数据；程序内部跳转用**栈枢轴**（L3，`MOV SP,ERn` 型 gadget）。

**第三层：程序从来不是"被当代码跑"的。**
它是"一段段 ROM 里现成的代码片段，用栈指针串起来"：
SP 就是链指针，每个槽末尾的 `POP PC` 把 SP 往前推 4 字节并跳进下一个 gadget。
常量和字符串**骑在链上**（`POP` 的内联数据），由 gadget 搬进 RAM。

```
        SP→ ┌──────────┬──────────┬──────────┐
            │ 槽1 →gadget│ 槽2 →gadget│ 槽3 →gadget│ …  链在 RAM 里，是"数据"不是"代码"
            └──────────┴──────────┴──────────┘
              每个 gadget 跑完 POP PC，就从链上取下一个槽
```

**第四层：调用 ROM 例程。**
把例程的机器码原样写进 `.bin`（解释器认出这段字节 = 发一个槽），参数由编译器搬进
`r0/r1/er2`；例程若以 `RT` 结尾，就先发一个 **rt-fix** 槽（扫描发现的：

```
A:      BL  T          ; T 处是 POP PC  → 把返回地址压进"硬件返回栈"，再吃一个链槽
A + 4:  BC  AL, U      ; U 处也是 POP PC → 例程 RT 回来后从这里继续吃链
```

），从而"以 RT 结尾的例程"也能安全地接回链上。

**第五层：launcher。**
7 字节 + 一个长度账本（写在输入/回放区），把 SP **枢轴**到链首；
链本身只是 RAM 里的一片数据（本项目默认 `0xEC00` 或 `0xD400`，可配）。

### 2. 有没有脱离原本 C 的语法糖？

**没有新增任何关键字或语法**。头文件就是普通 C（函数声明 + `#define`）。
但有**子集限制**——超出即明确报错，绝不悄悄生成错代码：

| 限制 | 原因 |
|---|---|
| 无运行时算术（表达式必须能编译期折叠） | 干净的 ALU gadget 只有 48 种固定寄存器/立即数组合 |
| 无 `if` / `while(cond)` | 条件分支缺一环原语（扫描结论见 `docs/step-7-…md`） |
| `for` 必须是**编译期常量次数**（编译期展开） | 没有条件分支，循环只能展开；语义等价于 `#pragma unroll` |
| 指针形参的实参必须是常量地址（数组名 / 字符串） | 内联时做**常量传播**；运行时指针待 A4 |
| 字符串 / 数组初值必须是常量 | 同上 |

也就是说：**在这些限制内是标准 C 语义**（函数、数组、结构体、`#include`/`#define`、
`for`(定次)/`while(1)`、`return`），超出则报错说明缺什么。

### 3. 有没有硬编码？

**编译器与解释器里没有任何 ROM 地址**（`grep -rn "0x221BE\|0x2BAD4\|0x17DE8" crop/ tools/`
无命中；唯一出现地址的地方是 `launcher.py` 注释里记录的实测值，不是取址依据）。

| 东西 | 怎么来的 |
|---|---|
| gadget / 栈枢轴 / 块写原语 / rt-fix | **现场扫描 ROM** 得到（字节匹配 + 指令形态匹配） |
| 语义例程（print / refresh / clear / screen-on） | `labels.conf` 里按**指令签名**解析，例如 `print-line = 221BE \| ST R0,0D137h ; BL * ; POP PC`（`BL *` 是通配），签名不匹配就**全 ROM 扫描** |
| 换版本（Ver） | 自动适配：VerC 的 print 落在 `0x221B2`、screen-on 落在 `0x09310`，源码一行不改 |
| 目标 ROM | 由 `--rom-dir` 传入 |

**唯一固定的常量是"机型事实"，不是 ROM 地址**：

* 屏幕缓冲区 `0xDDD4`、显存 `0xF800`、屏幕 192×64、字体 `0x0E/0x0A/0x08`、
  以及 "`r0`=字体、`r1`=行、`er2`=文本地址" 这个入口契约 —— 这些来自用户给的资料，
  写在头文件与注释里；
* 链址 / 变量区（`0xEC00`、`0xD400`、`0xD700`）是**注入位置**，
  由 `launcher.conf` / `--left-base` / `--data-base` 配置。

`labels.conf` 里的地址（如 `221BE`）只是**提示**：先在该地址试签名，不匹配就扫全 ROM，
所以它不是依赖。

## 问答二：这是压缩算法，还是针对显示文本的特定优化？

**都不是。它是通用的后端优化，而且严格说不是"压缩"。**

那处改动落在两条**与业务无关**的通用路径上：

1. **数据初始化发射**：任何 `unsigned char a[8] = {...}`、字符串常量、静态初值都走这条
   —— 按 `blk_pop_len` 一次喂满 8 字节（原来只喂 6）；
2. **常量赋值归并**：任何"地址相邻的一串常量写"都会归并成一次块写（上限 6 → 8）。

它**不是压缩算法**：没有任何编码/熵压缩，只是原来每块**白扔了 2 字节容量**
（`POP QR0` 明明一次能装 8 字节，历史代码只喂 6）。效果：

| | 之前 | 现在 |
|---|---|---|
| `hello_world` demo 链长 | 148 字节 | **114 字节**（VerF / VerC 一致） |
| 字符串初值写入 | 3 块 × 34 = 102 字节 | 2 块 × 34 = 68 字节 |

真正属于 CROP 的"压缩"在别处，而且同样是通用的：

| 机制 | 说明 |
|---|---|
| **L1 块复用** | `N` 条指令 → **1 个 4 字节槽**（匹配率越高越省） |
| **L2 等价转义** | `MOV Rn,#imm` → `POP Rn` + 链上数据 |
| **下一刀：pad=0 gadget** | 现在每块白付 12 字节 pad（gadget 尾巴的 `POP QR8 ; POP XR4`）；ROM 里有现成的 pad=0 gadget `0x17E7E`，可再砍一大截 |

**唯一"显示专用"的地方**：print 入口的 `R0` **兼作"字体大小"与"起始 x 像素"**
（`0x0E` = 14 px），所以"居中"要用**前置空格**微调 —— 这条写在 `rstdio.h` 与
`examples/hello_world.c` 的注释里，属于机型契约，不是编译器特性。

### 附：`hello_world`（114 字节）链的结构（便于对照上文）

```
D400  42 07 01 00 | 08 D7                     POP ER14 + 0xD708     ← 字符串池地址
D406  16 0F 01 00 | 20 20 68 65 6C 6C 6F 20   POP QR0 + "  hello "  ← 数据骑在链上
D410  E8 7D 01 00 | 00×12                     块写 gadget + 12 字节 pad  ← 下一刀要砍的
D421  42 07 01 00 | 10 D7                     POP ER14 + 0xD710
D427  16 0F 01 00 | 77 6F 72 6C 64 21 00 00   POP QR0 + "world!\0\0"
D433  E8 7D 01 00 | 00×12                     块写 gadget + pad
D444  D4 BA 02 00                             rt-fix  (0x2BAD4)
D448  7C 93 00 00                             screen-on (0x0937C)   ← 开显示，否则屏上什么都没有
D44C  D4 BA 02 00                             rt-fix
D450  6C 7F 00 00                             clear (0x07F6C)
D454  60 87 00 00 …                           refresh 参数准备
D460  BE 21 02 00                             print-line (0x221BE)
D464  72 87 00 00                             refresh (0x08772)
D468  42 07 01 00 | 66 D4 | 40 07 01 00       while(1)：POP ER14 + 回跳地址 + 枢轴
```

对应 C 源码（`examples/hello_world.c`）：

```c
#include "rstdio.h"
#include "rstdlib.h"

void main(void) {
    rscreen_on();                              /* ① 先开显示 */
    rclear();                                  /* ② 清屏幕缓冲区 */
    rprint(FONT_NORMAL, 20, "  hello world!");  /* ③ 居中打印（R0 兼作 x） */
    rrefresh();                                /* ④ 刷到显存 */
    while (1) { }
}
```

## 一句话总结

* **原理**：C → 真机器码 → "ROM 里现成代码片段的串联"，用栈指针当胶水，数据和常量骑在链上。
* **语法**：标准 C 子集，零新增语法；不够用的地方**明确报错**。
* **硬编码**：ROM 地址零硬编码（扫描 + 签名解析）；只有"机型事实"和"注入位置"是配置。
* **优化性质**：通用后端优化（数据发射 + 常量归并），不是文本专用，也不是压缩算法；
  真正的"压缩"是块复用/等价转义（及下一刀的 pad=0 gadget）。
