## 2. `examples/rstring.c` —— **之前的"✗"部分是核对地址写错了**（round 21 更正）

**教训**：`#include` 写在最前面 ⇒ 头文件里那些函数的**形参槽先被分配**，
所以 `msg` 根本不在 `0xD700`。实测布局（`--src` 现场编译得到）：

```
d@0xD700  s@0xD702  v@0xD70A  lo@0xD712  hi@0xD713  acc@0xD714  msg@0xD715
```

而我 round 13–19 一律按 `D700..D707` 去核对 `msg` ⇒ **假阴性**。
更硬的证据是 machine 里真实留下的值：

```
D712 = 41 ('A')   D713 = 42 ('B')      ← 正是 lo = msg[0]; hi = msg[1] 的结果
```

这两字节只有在 `rfill8` → `rcopy4(msg,"ABOP")` → `rput16(msg,65,66)` →
`lo = msg[0]; hi = msg[1]` **全部正确执行**后才会出现 ⇒ 搬运/数组/函数内联在真机上是好的。

对策（已实现）：`tools/crop-verify --src FILE --expect-var 名字=值` —— 变量地址由**现场编译**
结果解析，不再手写。凡是"链跑飞/没落地"的判断，今后都必须用 `--expect-var` 复核。

### round 22–23：找到了"链跑到一半就飞"的**精确位置**

```
链在 0xD400，跑完后 SP = 0xD488（= 链偏移 0x88）   PC = 0xEE518（飞了）
0xD726 = 43 52 4F 50  "CROP"   ← ★ 链里的第一个块写（字符串常量池初始化）**落地了** ✓
msg/lo/hi 仍然全 0
```

⇒ **链确实在跑，而且第一条块写（`POP ER14 + POP QR0 + LEA/ST`，round 1 就验证过的路径）成功落地**；
随后在链偏移 `0x88` 一带飞掉 —— 那一段正是 `rfill8`/`rcopy4` 里**一串连续的 `copy_var`**
（`POP ER12 + L/ST R7,-10h[BP]`）。

结论：**块写路径可用、`copy_var` 连用会出事**（单次 `copy_var` 在 copytest 里是通过的）。
两条不依赖 copy_var 的修法（下一轮做）：

1. **让 `rfill`/`rcopy` 落成块写**：`rfill8(d, 0)` 展开成 `d[0]=0; d[1]=0; …` 本来就是
   "地址相邻的常量赋值"，只要**形参在编译期被常量代入**（标量常量传播），codegen 的
   块写归并就会把它变成一条块写 gadget（已验证的路径）；`rcopy4(d,"CROP")` 同理
   （源是常量池里的已知字节）；
2. 或者给预处理器加**带参宏**，`#define rfill4(d,v) {…}` 直接展开成常量赋值序列。

### round 25：常量代入后的新结果 —— 跑得更远了，但**控制权又回到 OS**

```
链 @0xD400 310 字节（搬运已改走块写）  手按 [→] [=] 后：
msg[0xD715] = 43 ('C')           ← ★ rcopy4 的第一字节落地了（之前是全 0）
hi/lo 仍为 0
PC = 0x9216   SP = 0xEE34        ← ★ 回到 OS 空闲栈，**没有停在 rhalt() 的 while(1)**
D180(输入区) = FD 24 F0 EB 8F A6 23   ← 注意第 6 字节被 OS 改写（原样是 23）
```

两点结论：

1. **常量代入生效**：`rfill8`/`rcopy4` 走块写后，`msg` 开始被真正写入（拿到 'C'）；
2. **丢控制权的位置在链尾**：程序结尾是 `rhalt()`（函数内联出来的 `while(1)`），
   但机器回到了 OS 空闲栈 —— 说明**链尾那段跳转/锚点不对**（或执行到链尾就掉出去了）。
   下一步：把 `rhalt()` 换成 `main` 里直接写 `while(1){}`（hello.c 那种已验证的形式）做对照，
   若那样能停住，就是"**内联函数里的 `while(1)`**"这个组合在长链上有问题。

### round 26–27：对照实验 —— 与"内联函数里的 while(1)"无关

把结尾换成 `main` 里直接 `while(1){}`（hello.c 已验证过的形式）后，结果**完全一样**：

```
msg[0xD715] = 43 ('C')   ← 只有 rcopy4 的**第一字节**落地，第 2~4 字节没写
PC = 0x0946C（跳进了 ROM 的复位/启动流程那一带）   SP = 0xD486（还在链区）
```

⇒ 与链尾写法无关；**跑飞点在"第一次 `copy_var` 成功之后、紧接着的第二次 `copy_var` 处"**。

对照事实：`copytest`（`b = a`，只做**一次** `copy_var`）通过；这里第一次也成功（'C' 落地），
第二次就飞。所以怀疑点是**连续 `copy_var` 时链的排布/记账**：

* 每次 `copy_var` = `pop_block(6B) + block(4B) + pop_block(6B) + block(4B)` = 20 字节；
* `L R7,-10h[BP]`（读槽）与 `ST R7,-10h[BP]`（写槽）是两条**各自带 `POP PC`** 的单指令 gadget，
  中间夹一个 `POP ER12 + 2 字节` —— 需要逐字节核对：第二次的 `POP ER12` 内联数据
  是否被前一条 `ST` gadget 的 `POP PC` 正确地对齐（**偏移错 2 字节就会读到垃圾基址**，
  然后 `ST` 写到别处 → 链随后飞进复位流程）。

**round 28（离线判定）：`b = a; c = b;` 在 lifted 模拟器里完全正确**

```
链 62 字节，unsupported=0
VM: a=7  b=7  c=7   ✅（两次连续 copy_var 都对）
链字节（人工可核对）：
  C0 93 00 00 00 D7 07 00 D2 03 02 00      a = 7   （POP XR0 + 地址/值 + ST）
  EE 63 01 00 10 D7 52 3F 01 00            POP ER12+0xD710 ; L R7,-10h[BP]
  EE 63 01 00 11 D7 24 0F 01 00            POP ER12+0xD711 ; ST R7,-10h[BP]
  EE 63 01 00 11 D7 52 3F 01 00            POP ER12+0xD711 ; L R7,-10h[BP]
  EE 63 01 00 12 D7 …                      POP ER12+0xD712 ; …
```

⇒ **链的编码与记账是对的**（每段 `pop_block` = 4 字节槽 + 2 字节内联数据；`L`/`ST` 各 4 字节槽），
"两次搬运之间的 2 字节错位"这个假设**不成立**。

于是真机上"只落地 'C'"的原因要换个方向找，下一轮做两个判定：

1. 真机跑最小样例 `a = 7; b = a; c = b;`（62 字节链）——**判定"两次连续 copy_var"在真机上是否本身就会出问题**；
2. 若它也失败，就把 `rcopy4` 那种**源是字符串池**的搬运单独做成样例（`msg[0..3] = pool[0..3]`），
   判定是不是"源地址在只读池"这一形态的问题。

**round 29–30（真机判定①）：`a = 7; b = a; c = b;`（62 字节链）**

```
D700 = 07 ✓     D701 = 00 ✗     D702 = 00 ✗
PC = 0x203D4    SP = 0xD40C（= 0xD400 + 12，正好在常量写那一块之后）    D180 已导入 launcher ✓
```

⇒ **常量写 `a = 7` 落地；紧接着的第一次 `copy_var`（`b = a`）没落地**，CPU 停在
`ST R2,[ER0]` gadget 的尾巴上（`PC=0x203D4`）。

对照 `copytest`（`a = 7; b = a; c = 9`）**是通过的**（`07 07 09`）——两者唯一的区别是
**第一次 `copy_var` 后面跟的是"另一次 copy_var"而不是"常量写"**。

所以修正后的结论：**不是"第二次 copy"坏，而是"copy 后面还跟着 copy"时第一次就坏**
（`copytest` 里 copy 后面跟的是常量写，所以没事）。最可能的原因是
`L R7,-10h[BP]` / `ST R7,-10h[BP]` 这两条 1 指令 gadget 与其后 `POP ER12` 的**内联数据
在真机取指流水上的时序**（单次没事、连着两次就被打断），或某次 `ST` 改到了**紧跟其后的槽**。

下一轮：把 `b = a; c = b;` 改成**中间插一条常量写**（`b = a; c = 9; d = b;`）验证
"cop 后必须跟常量写"这个规律；若成立，就在 `copy_var` 的实现里**每两次搬运动作之间强制插入
一个 4 字节的间隔槽**（或改用块写 gadget 做搬运）来规避。

**round 31+（暂停+单步：链其实在正确执行！）**

在"卡住"的现场 `PC=0x203D4 SP=0xD40C` 上 `pause` 再 `step_into` 四次：

```
暂停:  PC=203D4  SP=D40C      SP 处 16 字节 = EE 63 01 00 | 10 D7 | 52 3F 01 00 | C6 8D 00 00
单步1: PC=163EE  SP=D410      ← POP ER12（吃掉 0xD40C 那一格 = 0x163EE ✓）
单步2: PC=163F0  SP=D412      ← 吃掉内联基址 0xD710 ✓
单步3: PC=13F52  SP=D416      ← L R7,-10h[BP] ✓
单步4: PC=13F54  SP=D416
```

⇒ **链在真机上是一条条正确执行的**（取槽 → 取内联基址 → 读槽 → …），
`PC=0x203D4` 只是**采样时刻**恰好落在常量写 gadget 的尾巴上，不是卡死。
但 SP 停在链的**前段**（≈0xD40C）而不是链尾 `while(1)`，说明这条链**在反复从头跑**，
而 `b = a` / `c = b` 的结果没有留下来（`D701/D702 = 0`）——这两点合起来说明：
**每次循环重跑时，前面写下的结果被清掉了**（最可能：机器自己的中断/任务在动 `0xD7xx` 那片，
或者链尾的跳转其实回到了链首）。

下一轮（真机 + 单步就能定）：
1. 在链尾 `while(1)` 处设 `add_memory_breakpoint(pause=true)`（对链尾 slot 地址设读断点），
   看它到底跳到链首还是链尾；
2. 同时给 `0xD700..0xD702` 设**写**断点，记录每次写入的 PC 与值 —— 就能看出"谁把它们清掉了"。

更早的排查：
对照真机现象；若模拟器正常而真机失败，就把两次之间的链字节与偏移逐字节打印出来核对
（重点看 `interp.py` 对 `pop_block` 的 `chain_bytes` 记账：`4 + nbytes` 是否与实际发射字节一致）。

## 2'. rstring 更早的排查记录（round 13–19）

```
注入：428 字节链 @0xEC00（回读一致）、launcher @0xD248、账本 0xD244=07、D700..D70F 清零
手按 [→] [=] 后：
  D180(输入区) = FD 24 F0 EB 8F 23 42   ← 【→】导入成功 ✓
  D700..D707   = 00×8    D708/D709 = 00/00    ← 程序的写内存没落地
  屏幕非零字节 = 15（只有 OS 光标）；F800 == DDD4 的副本关系为 True
  PC = 0xFCB9E（跑到链外去了）  SP = 0xEDB6（= 0xEC00 + 438，已经越过链尾 0xEDAC）
```

解读：**链被执行了**（SP 从 0xEC00 走到链尾之外 ⇒ 一路吃链），但

* 变量区的写没有落地；
* 结尾的 `rhalt()`（`while(1)`）没有把 SP 钉住，而是**跑过链尾、跳到 0xFCB9E**。

对比同一条流程下 **`copytest.c`（54 字节）完全正确**（`07 07 09`），所以怀疑点：
①链尾 `while(1)` 的锚点/枢轴在这条更长的链上算错了；②或长链执行途中把链自己踩了
（链就是栈：ROM 例程的 PUSH/POP 会写 SP 以下，即**已经走过的**链字节 —— 若某处
越过了当前 SP 就会改到"还没用到的"槽）。

**round 16（链挪到 `0xD400` 后的结果）：**

```
D180 输入区 = FD 24 F0 D3 8F 23 42   ← 【→】导入成功 ✓
D700..D70F = 全 0                    ← 变量区仍未落地
SP = 0xD488（链 @0xD400，即走到第 136 字节）   PC = 0xEF124（飞了）
屏幕 = ram.dmp 里的旧画面（不是本次输出）
```

⇒ 链**在执行**，但走到第 ~136 字节就飞。按链结构算，这个位置正好是
**连续 16 次 `copy_var` 之后、还没进第一个库例程调用**。
`copytest`（只做 1 次 `copy_var`）是通过的，所以怀疑点收窄为：
**连续多次 `copy_var`（`POP ER12 + L/ST R7,-10h[BP]`）在真机上会累积出问题**
（BP 基址算法在真机与模拟器不一致 / 某一步踩到链本身）。

上一轮的假设"链压到 OS 栈区 `0xEDxx` 所以飞"**已被这次结果排除**（挪到 `0xD400` 后照样飞）。

下一轮：把 `rstring.c` 二分——先只留 `rcopy4` + `rprint` + `rhalt`（去掉 `rfill8`/`rput16`），
确认是"长度/尾部跳转"问题还是某个具体语句的问题。

## 2'. 更早的尝试（round 3–5）

**离线（真 ROM 的 lifted 模拟器）跑这条 428 字节链，结果完全正确：**

```
msg = 41 42 4F 50 00 00 00 00    hi=66 lo=65      ← 与 C 语义一致（rcopy4 + rput16）
```

**真机（round 4，把机型目录里的 `ram.dmp` 移走后冷启动）：**

```
启动 PC=09216 SP=EE34
AC → 写 launcher/账本/链 → [→] [=]
链回读一致 True
按键后 PC=09216 SP=EE34        ← 控制权又回到 OS
D137=0E                        ← 不能作为证据：OS 自己打印文本时也会写 14
D700..D707 = 00 00 00 00 00 00 00 00    D708,D709 = 00 00     ← 程序的写内存没落地
F800[32:56]==DDD4[24:48]: True（屏幕上是 OS 自己画的那一屏，120 个非零字节）
```

结论：**程序本身没问题**（离线语义逐字节正确、翻译 0 条不支持），
问题在真机这一段流程：注入后链没有真正跑起来（或跑了几步就被 OS 接管）。
`hello.c`（128 字节链）在同样流程下是通过的，所以怀疑点收窄到：
链长 428 字节（`0xEC00~0xEDAC`）是否撞到机器自己的东西、以及 OS 的输入/历史状态。

**round 5 的决定性实验（内存监视）：**

```
给 0xEC00（链区）设"读"监视 + 给 0xD700（msg）设"写"监视 → 清输入行 → 写 launcher/账本/链 → [→] [=]
链被读: 0 次     msg 被写: 0 次     D137=0E    D700=00×8
```

⇒ **链区一次都没被读过**：触发（launcher 那条路）根本没生效，**与链长无关**。
所以问题不在 428 字节的链，而在"按 `→` `=` 让回放区导入并执行"这一步现在的 OS 状态下不成立
（round 1 成功过，说明是**机器状态相关**，不是通道本身坏了）。

下一轮要查的（按顺序）：
**round 6 的观察（冷启动，写监视 0xD180 / 0xD244 / 0xEC00）：**

```
启动 / 按 AC / 按 [→] / 写 launcher+账本 / 再按 [→] / 按 [=]
  → 三个地址的"写"命中**全是 0**；0xD180 始终保持 00×8
```

⇒ 不是"回放区被覆盖"，而是**按键根本没有作用到计算器上**（OS 连自己的输入缓冲都没改），
于是后面所有步骤都无从谈起。结合 round 1（那时成功）与 round 3-6（都不行）的差别：
round 1 用的是模拟器**原有的 RAM 快照**（你之前跑出来的状态），
而 round 3-6 我为了让状态"干净"把 `ram.dmp` 移走了 —— 冷启动后机器不在可用的输入界面，
`AC`/`→`/`=` 自然不生效。**原始的 `ram.dmp` 已经放回原处**。

**round 7（把 ram.dmp 放回后）：触发是好的，问题缩小到一个具体机制**

```
对照 hello.c  ：链回读一致 ✓   D137=0E ✓   屏幕 8% 非零（文字在）      ← 真机通过
rstring.c     ：链回读一致 ✓   但 D700 = 01 D7 10 0E 0B 00 00 00 ✗    ← 数据区没被写
```

`hello.c` 的写法只用 `write_byte_imm`（`POP XR0 + ST R2,[ER0]`）和块写 gadget；
而 `rstring.c` 的每一次搬运/填充都走 **`copy_var`**（BP 槽：`POP ER12 + (addr-off)` →
`L R7, off[BP]` → `ST R7, off[BP']`）。离线 lifted 模拟器里 `copy_var` 是对的，
但**它在真机上从来没有被单独验证过**（第 4 步只验证过块写那条路）。

⇒ **当前最可信的假设：`copy_var`（BP 相对 L/ST 槽）在真机上不成立**，
所以 `msg`/`hi`/`lo` 全是原值，而 `hello.c`（不碰 copy_var）一切正常。

**round 8 判定实验（`a = 7; b = a; c = 9;`，只用 write_byte_imm + copy_var）：**

```
链回读一致 ✓
[D700] 期望 07 实际 01 ✗    [D701] 期望 07 实际 D7 ✗    [D702] 期望 09 实际 10 ✗
```

**连 `write_byte_imm`（`a = 7`）都没落地** —— 所以问题不在 `copy_var`，而在
**数据区地址 0xD700 本身在这台机器上不是"我们能留东西"的地方**（它一直保持
`01 D7 10 0E 0B ...`，像是 OS/栈里的东西）。

回看已确证的项：真机上真正读到的效果是 **`D137`（ROM 例程写进去的字体全局）** 和

**"用户变量区放哪"这件最基础的事从来没有在真机上验证过**（第 4 步只验证了 0xD710，

1. 用 MCP 往几个候选区（`0xD400`、`0xD710`、`0xEDC0` …）各写一段特征字节；

更早的判定实验（已被上面这条取代）：

2. 若按键仍不生效，就**请你手按** `[→]` `[=]`（MCP 只负责读写内存，这条路你已经用过）；
3. 之后再补 rstring 的真机记录。

## 3'. 更早的记录（round 3，同一问题）

程序（`#include <rstring.h>` + `<rstdlib.h>`）：清零 `msg` → `rcopy4(msg,"CROP")` →
`rput16(msg,65,66)` → 打印 → 刷新 → `rhalt()`。
编译/翻译没问题（两版 ROM 都是 171 条指令 / 428 字节链 / **0 条不支持**）。

真机三次尝试的现象（每次都确认过链写对了）：

```
链回读一致 True（0 个字节不同）
按键后  PC=09216（OS 空闲循环）  SP=EE34（OS 栈）     ← 说明**触发没生效**，控制权还在 OS 里
[D700] = 01 D7 10 0E 0B 00 00 00                     ← 不是程序的 msg
屏幕缓冲区非零字节 = 15（只有 OS 自己的光标竖条）
```

`hello.c` 在同样的注入流程下是通过的，所以问题不在链本身，最可能是**机器状态**：

* 模拟器退出时会把 RAM 存进机型目录的 `ram.dmp`，下次启动恢复 —— 于是 OS 的输入行/
  历史（`0xD248` 那一片）不是干净的，AC/`→`/`=` 的语义和首次启动时不同；
  VerC 那次也观察到"按 `→` 之后 OS 会把自己的历史写回 `0xD248`"。
* 本轮顺手修了 `tools/crop-verify` 的一个顺序问题：**AC 必须在写内存之前按**
  （之前是写完再按 AC，会把刚写进 `0xD248` 的 launcher 冲掉）。

下次要复现的步骤（还没做）：
1. 启动前把机型目录里的 `ram.dmp` 移走（或先 `MCP reset` 再等机器回到空闲循环）；
2. 按 AC → 写 launcher/账本/链 → 按 `→` `=`；
3. 读 `0xEC00`、`PC/SP`、数据区与屏幕缓冲区，把结果补到本节。
