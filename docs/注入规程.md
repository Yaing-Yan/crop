# 注入规程（真机验证版 · VerC 已通过）

## 验证记录（两个版本都通过）

| 版本 | ROM 目录 | launcher（写 `0xD248`） | 结果 |
|---|---|---|---|
| **VerC** | `models/fx991cnxVirtual` | `FD 24 F0 EB 7B 23 42`（枢轴 `0x2237A`） | `0xD710..D715 = 11 45 14 19 19 81` ✅，`SP=0xEC26` |
| **VerF** | `fx991cnxfVirtual` | `FD 24 F0 EB 8F 23 42`（枢轴 `0x2238E`） | `0xD710..D715 = 11 45 14 19 19 81` ✅，**`PC=0x10742`（链内循环 gadget）**，`SP=0xEC26` |

同一份 C（`b0..b5 = 11 45 14 19 19 81`）、同一份链字节（44 B），
**两个 Ver 的 launcher 由各自 ROM 扫描推导**（只差尾部一个字节），都真机跑通。
VerF 那次的 `PC=0x10742` 直接落在链的循环 gadget 上，可确认 CPU 正在执行我们生成的链。

## 一、三个地址各是什么

| 地址 | 角色 | 说明 |
|---|---|---|
| `0xEC00` | **链存放处（左地址）** | 必须避开机器自己的栈：实测栈在 `0xE9xx~0xEBxx`（SP 观测值 `0xEE34`/`0xEB26`/`0xEA06`）。放 `0xE9E0` 会被压栈踩烂 |
| `0xD248` | **回放区 = 输入缓冲区（源）** | launcher 要注入**这里**，不是 `0xD180` |
| `0xD180` | **输入区（目的地）** | 按【→】把 `0xD248` 的内容导进来；直接写这里会被覆盖 |
| `0xD244..0xD247` | **长度/光标账本（实测有效）** | 只写内容不写长度 → 【→】什么都导不进来（会清空 `D180`） |

## 一·补：怎么把 MCP 拉起来（2026-09-13 实测）

```bash
cd <EMU_DIR> && ./CasioEmuMsvc models/fx991cnxfVirtual      # ← 机型目录必须当参数传！
```

* **McpPlugin 只在"模型已经跑起来"时才加载**：裸跑 `./CasioEmuMsvc` 会停在选机型界面，
  `127.0.0.1:3001` 根本不监听（`grep -c McpPlugin /proc/PID/maps` 为 0 可以确认）。
* 本机 GUI **不接收合成输入**：uinput 绝对指针能让光标移动，但点击/按键都到不了这个
  SDL/ImGui X11 客户端；XTest（`tools/xinput`）同样无效。所以"用鼠标点选机型"不可行。
* 启动后 `tools/mcp-call tools` 应列出工具；`tools/mcp-call call get_status` 看 PC。
* 一条命令做完注入+按键+回读：`tools/crop-verify --rom-dir <机型目录> --bin <程序.bin> --data-base D700 --expect D137=0E --screen DDD4 E3D4`
  （`read_memory` 新版回 JSON `{"address":…,"bytes":[…]}`，工具已兼容。）

## 一·补二：按键必须**手按**（2026-09-13 实测，重要）

| 结论 | 证据 |
|---|---|
| MCP 的 `keyboard_code` 在这台机器上**不生效** | 给 `0xD180`/`0xD244`/`0xEC00` 设写监视，走完整流程后写命中全是 0；链区"读"命中也是 0 |
| **手按**【→】【=】可靠 | 同一条链、同一份注入，人按之后 `D700/701/702 = 07 07 09`（与 C 语义完全一致） |
| "直接设 `SP`/`PC` 启动链"这条捷径**不可靠** | 同样注入下直接设 `SP=0xEC04/PC=链首槽` 跑出 `09 09 09`（机器状态/数据段不对），别拿它做验证 |
| `ram.dmp` 不要动 | 它是可用输入界面的一部分；清掉之后按键/回放都不是原来的行为 |

所以真机验证流程定为：**注入 → 请人按 [→] [=] → 读回**。

## 一·补三：**用 computer-use 按计算器按键**（2026-09-13 实测，最省事）

MCP 的 `keyboard_code` 键码表不完整（实测 `0x30` 打出来的是 `+` 不是 `=`），
但**用主机键盘发按键完全可用**（SDL 映射）：

| 主机键（DSH 工具 `press_key`） | 计算器按键 | 验证方式 |
|---|---|---|
| `Right` | **【→】** | 按下后 `0xD180` 出现 launcher 字节 `FD 24 F0 D3 8F 23 42` ✓ |
| `Return` | **【=】** | 按下后链开始跑：`SP` 落到链区（如 `0xD438`）、`0xD137=0E`、屏幕缓冲区被绘制 ✓ |

所以自动化流程是：**MCP 读写内存 + computer-use 按 `Right`/`Return`**，不需要人工。
（`keyboard_code` 仅在个别键上可用；`=` 千万别用它。）

## 二、注入步骤（MCP write_memory）

```
1. 链   → 0xEC00   44 字节（由 crop-rop / rgcc --left-base EC00 生成）
2. launcher → 0xD248
     VerC: FD 24 F0 EB 7B 23 42
     VerF: FD 24 F0 EB 8F 23 42
     （FD 24 前缀 | EB F0 = EC00-10h，给 SP | 尾部 3 字节 = 该 Ver 枢轴编码）
3. 长度 → 0xD244 = 07 07 07 07
4. 清空 0xD180（否则残留旧内容）
5. 按【→】（把 D248 导进 D180），再按【=】（触发 ROP）
```

## 三、验收

```
0xD710..D715 = 11 45 14 19 19 81      ← C 程序语义
SP 落在 0xEC00 附近（实测 0xEC26）      ← 枢轴 + 回跳都在工作
```

## 四、踩过的坑（都已在代码/流程里修掉）

| # | 坑 | 现象 | 修法 |
|---|---|---|---|
| 1 | launcher 注到 `0xD180`（目的地） | 按【→】后 `D180` 被清空，`=` 跑的是旧账本 | 注到源区 `0xD248` |
| 2 | 只写内容、不写长度账本 | 按【→】导不进来（`D180` 全 0） | `0xD244..0xD247 = 07` |
| 3 | 块写 gadget 从外层起点 `0x17DE2` 进入 | 前面的 `L QR0,[EA+]` 用垃圾 EA 把 R0..R7 冲掉 → `D710` 被写成 `C4 9C 00 70 E5 C8 00 7A`（确定性垃圾） | 改从 `LEA [ER14]`（`0x17DE8`）进入 |
| 4 | 链放在 `0xE9E0` | 被机器栈周期性踩（第 10 字节起变成 `38 07 01 00` = 别的返回地址） | 放到 `0xEC00` |
| 5 | MCP 按键太短（0.08s） | 键盘扫描直接漏掉，`PC/SP` 一直不动 | 长按 ≥0.9s（或人工按） |
| 6 | 机器卡死在旧 ROP 里时继续注入 | 注入的字节毫秒级被踩（`SP` 停在链区） | 先复位（关机→开机），确认 `PC=0x91AA / SP=0xEE34` 再注入 |
